# Workpath: product (the solar harness's own code: a number, a test, a command, a window)

The product's rows, beside `docs/paths/process.md`'s: a task, the two to five files to open first and nothing else
yet, the contract to read, the tests to run before and after. Written at Tune-up pass 6 from four debriefs that met
the same gap (J-039, J-041, J-043, the architecture review of J-041). The modules, what each may import and why, are
`docs/modules.json`; the project layer is the one place modules meet (MOD-02, MOD-05).

| Task | Start here | Contract | Tests |
| --- | --- | --- | --- |
| A KPI or a report's number: a formula, its rounding, its gaps | `docs/CONTRACT.md` (its SOL section), `solarpunk/kpi/` (the number's file), `solarpunk/project/reports.py` or `solarpunk/project/orchestrator.py` (`kpis_for`) | SOL-03, SOL-06 to SOL-11, SOL-13; a new number arrives with its contract section and worked example first | `test/solarpunk/test_kpi.py`, `test/solarpunk/test_output.py`, `test/solarpunk/test_mirror.py` (SOL-07 to SOL-10 only) |
| A remote test (a diagnostic): add one or change one | `solarpunk/remote/tests/power_under_rated.py` (the shape: `KINDS`, `CLAUSES`, `run`), `solarpunk/remote/registry.py`, `solarpunk/leaf/asset_types.json` with `docs/ASSET-MAINTENANCE-LIST.md` (a kind's `Tests:` line, one line, the two files together) | SP-010, SOL-03; `solarpunk test add <name> --clause <id>` scaffolds one; a clause it names is a row of `docs/CLAUSE-REGISTER.md` | `test/solarpunk/test_diagnostics.py`, `test/solarpunk/test_remote.py`, `test/solarpunk/test_project_run.py`, `test/solarpunk/test_demo.py` (their counts follow the registry since SP-017: adding a test is one file and its line in the maintenance list) |
| A command-line command | `solarpunk/cli/main.py` (the handler, the parser and the `HELP` list), `solarpunk.cmd` (the routing words, twice: the comment and the `for` line) | MOD-02: one project call, no logic | `test/solarpunk/test_cli_tests.py` (the command count), `test/test_launcher.py`, `test/solarpunk/test_cli.py` |
| A window, or a widget in one | `solarpunk/ui/__main__.py` (the wiring), the window's file, its project call (`solarpunk/project/surface.py` or `solarpunk/project/reports.py`), `solarpunk/ui/chart.py` or `solarpunk/ui/glyph.py` (the pure half: no tkinter, so the fast loop tests it) | SP-007, SP-010: ui imports project and the leaf alone | `xvfb-run -a .venv/bin/python -m pytest -q test/solarpunk/test_ui*.py` (the fast loop's `python3` has no tkinter; the fast checks run these under xvfb since SP-017, and say `note: window tests not run` where they cannot; a fresh container's venv may lack tkinter: `apt-get install -y python3-tk`); then render the changed window under xvfb and read the screenshot before landing: this phase's two UI bugs were found only by looking (J-043, J-045) |
| The fleet, a fault, a work order | `solarpunk/fleet/registry.py`, `solarpunk/faults/ledger.py`, `solarpunk/workorders/ledger.py`, `solarpunk/project/orchestrator.py` (the joins) | SOL-04, SOL-05, SP-011, SP-015 | `test/solarpunk/test_fleet.py`, `test/solarpunk/test_faults.py`, `test/solarpunk/test_workorders.py`, `test/solarpunk/test_project.py` |
| The feed, the receiver, the scheduled run | `solarpunk/feed/client.py`, `solarpunk/receiver/server.py`, `solarpunk/project/run.py` | SP-006, SP-008 (in part superseded by SP-015), SOL-06 | `test/solarpunk/test_feed.py`, `test/solarpunk/test_receiver.py`, `test/solarpunk/test_project_run.py` |
| The demo | `solarpunk/ui/demo.py`, `DEMO.md` | the three colours and who wears them (the module's docstring) | `test/solarpunk/test_demo.py`; `python3 -m solarpunk.ui --demo` under xvfb, its screenshot read |
